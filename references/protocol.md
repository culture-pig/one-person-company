# 运转协议（Protocol）

## 一、双通道，硬规则

公司只有两个通道。**每条消息必须且只能落在一个通道里，由消息类型决定，不由模型自由判断。**

### 群聊（channel = `group`）
公开广播。只允许三种员工消息，外加一种老板消息：

| 类型 | 谁发 | 内容 | 例 |
|---|---|---|---|
| `TASK` | 项目经理 | 派活：编号、负责人、交付物、验收标准 | `#T-003 派给 @架构师：产出接口文档与表结构，验收=每个接口有入参出参错误码` |
| `PROGRESS` | 任何人 | 进度：百分比 + 一句话在做什么 | `#T-003 进度 60%，接口定义完成，在建表` |
| `DELIVER` | 任何人 | 交付：产物路径 + 一句话结论 | `#T-003 交付 05-架构/，共 12 个接口 6 张表` |
| `BOSS` | 老板 | 提需求 / 下指令（第 1 步） | `我想加一个按周汇总的视图` |

**群里禁止出现**：方案比较、风险判断、请示决策、抱怨、寒暄、"我觉得可能"。一句都不行。

老板在群里发话走 `BOSS`，含义就是"这是新需求"。员工看到后不要就地讨论，由项目经理转成 `TASK` 再开工。

### 私聊（channel = `dm:<员工代号>`）
一对单线。只允许三种类型：

| 类型 | 含义 | 期望老板的动作 |
|---|---|---|
| `CHALLENGE` | 方案分歧：我认为该走 A，但有人要走 B | 选一个 |
| `RISK` | 风险预警：会延期 / 会返工 / 有阻塞缺陷 | 知情，必要时干预 |
| `DECIDE` | 请求裁决：缺业务假设或需要拍板 | 回一句话 |

**私聊必须给"选项"，不能只给"问题"。** 格式：

```
【DECIDE】关于登录方式
选项 A：手机号+验证码（快，需短信通道）
选项 B：邮箱+密码（慢，零外部依赖）
我建议 A，理由是首版用户都是手机用户。
请回复 A 或 B。
```

老板回一句话，员工把结论**回写群聊**（以 `PROGRESS` 形式，写"已裁决：..."），私聊闭环。

### 第三条出路：归档

不是所有私聊都要老板拍板才能结束。两条路：

| 出路 | 用于 | 命令 |
|---|---|---|
| `DECISION` | 真要老板在方案里选 | 老板回复后记一条 DECISION |
| **归档** | 风险已被解决、或只是知情提醒 | `opc ack --id M020` |

**归档不是删除**，原文仍在私聊记录里。它只是把这条从"等你拍板"里摘出来。

不归档的后果很具体：`RISK` 类型永远挂着，董事长办公室的角标从 2 涨到 5 再到 10，老板最后学会无视它 —— 那时候真正需要他拍板的事也一起被无视了。**角标一旦长期不为零，这个通道就失效了。**

判断标准：这条消息会不会改变老板的下一步动作？
- 会 → 留着，等裁决
- 不会，只是"让他知道" → 归档，把内容写进交付说明或 ADR

### 为什么必须这样
模型天然爱在群里解释和商量。一旦允许，群聊会退化成一堆自我辩论，老板看不到进度。所以通道是**结构约束**，不是礼貌建议。

## 二、三类门禁（Gate）

阶段之间不能自动流转，必须过门禁。门禁由项目经理判，判据是清单，不是感觉。

| 门禁 | 位置 | 通过条件 |
|---|---|---|
| **G1 立项门** | 第 2 步后 | 目标可验收、范围含 out-of-scope、里程碑有日期 |
| **G2 方案门** | 第 4 步后 | 粗需求覆盖老板原话每一条、周期与资源已确认 |
| **G3 设计门** | 第 6b 步后 | 每个 PRD 功能都有对应接口；每张表有主键索引；选型有理由 |
| **G4 上线门** | 第 8 步后 | 测试报告结论为"可以上线"，且无阻塞级缺陷 |

判"打回"时，必须写明**打回理由 + 补什么**，不能只说"不行"。

## 三、产物链

每个阶段产物落到固定文件名。**下游开工前必须先读上游产物**，读不到就停下报错，不许凭记忆开工。

```
00-需求原话.md      老板原话，不改写
01-立项书.md        项目经理
02-PRD-粗.md        产品经理（粗）
03-PRD-细.md        产品经理（细，方案锁定后）
04-原型/             UI设计
05-架构/            架构师
06-测试报告.md      测试
07-部署记录.md      运维
src/                程序员
```

产物是公司的记忆。新开会话、换 agent、换模型，读这些文件就能接着干。

## 四、模型档位

角色不绑死具体型号，绑**档位**。档位由宿主的模型路由能力解析，所以换套餐、换模型都不用改配置。

| 档位 | 用途 | 谁在用 |
|---|---|---|
| `reasoning` | 强推理，慢而准 | 项目经理、架构师 |
| `default` | 主力档，均衡 | 产品经理、UI设计、程序员 |
| `lite` | 快而省 | 测试、运维 |

**派活方式**：涉及该员工实质产出时，用子任务派发并把档位传下去；宿主不支持指定档位时，降级为在当前会话内按角色 prompt 执行，但要在群聊 `PROGRESS` 里注明"降级同模型执行"，不假装是一人一模。

档位可重复 —— 多个岗位用同一档位是正常配置，不需要每个岗位都不同。

## 五、一轮完整运转长什么样

```
老板：「我想做一个记账小程序」
  ↓
[群聊] @项目经理 TASK #T-001 立项
[群聊] @项目经理 PROGRESS #T-001 进度 100%
[群聊] @项目经理 DELIVER #T-001 01-立项书.md，范围 3 项，不做多账本
  ↓ G1 通过
[群聊] @产品经理 TASK #T-002 粗需求
  ↓ 产品经理发现「不做多账本」和老板原话冲突
[私聊 pd] CHALLENGE 老板原话提到"给老婆一起记"，可能需要多用户
        选项 A 单用户先做 / 选项 B 直接做多用户（多 5 天）
  ↓ 老板回「A」
[群聊] @产品经理 PROGRESS #T-002 已裁决：单用户。继续
[群聊] @产品经理 DELIVER #T-002 02-PRD-粗.md，7 个用户故事
  ↓ G2 通过
... 依次到运维
```

注意：**群聊里从头到尾看不到"选项"和"我觉得"**。老板的注意力只花在私聊那三条待裁决上。

## 六、老板的注意力预算

一人公司最贵的资源是老板的注意力。所以：

- 私聊**每轮最多 3 条**待裁决，多了项目经理要先合并、先自己拍掉不重要的。
- 每条私聊必须自带推荐选项，让老板能只回一个字母。
- 群里不 @老板。群里只有员工之间的事，老板想看就看，不 @ 他。
